# Decisions

Changes to, and clarifications of, `docs/PLAN.md`. Agreed 2026-10-04 before Phase 0. Where this file and the plan disagree, this file wins.

## Stack

| #   | Decision                                                                                                                                       | Reason                                                                                                                  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| D1  | **Next.js 16** (not 15), Tailwind 4, Zod 4, React Compiler on                                                                                  | 16 is the current stable. Request interception lives in `src/proxy.ts` (Next 16 renamed `middleware` to `proxy`).       |
| D2  | Cache Components (`cacheComponents`) stays **off**                                                                                             | PPR is incompatible with nonce CSP, and next-intl support is still partial. Classic ISR (`revalidate`) covers the menu. |
| D3  | Supabase: **hosted free project** for development and the demo; the **full local Supabase stack runs in GitHub Actions** for RLS and E2E tests | No Docker on the dev machine. Actions runners have Docker.                                                              |

## Security headers

| #   | Decision                                                                                                                                                                                                                                                        | Reason                                                                                                                                                                                                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D4  | **Two CSP levels.** Nonce + `strict-dynamic` on routes that handle accounts, orders or staff data (`/checkout`, `/account`, `/track`, `/dashboard`, `/admin`, `/login`). A nonce-free CSP (`script-src 'self' 'unsafe-inline'`) on public marketing/menu pages. | Nonces force dynamic rendering, which would remove static/ISR pages and hurt the Lighthouse target. Public pages render no user-supplied content.                                                                               |
| D5  | `style-src 'self' 'unsafe-inline'` on all routes                                                                                                                                                                                                                | React SSR `style={}` attributes, Framer Motion and Leaflet need inline styles. A nonce in `style-src` would make browsers ignore `'unsafe-inline'` and break them. Script injection is the real XSS risk and stays locked down. |

## Business rules (defaults, all configurable in `settings`)

| #   | Rule                                                                                                                                                                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | Bill order: subtotal → promo discount → service charge (10%) → VAT on (subtotal − discount + service charge) → delivery fee (no VAT). Default VAT 18%, flagged "verify before going live". All amounts integer cents, rounded half-up per line. |
| B2  | Loyalty: earn 1 point per Rs. 100 of subtotal after discount; redeem 1 point = Rs. 1, capped at 20% of the bill.                                                                                                                                |
| B3  | Delivery radius is straight-line (haversine) distance from the branch.                                                                                                                                                                          |
| B4  | Poya and other holidays live in a dated table admins can edit, seeded from the official calendar.                                                                                                                                               |
| B5  | `/dashboard` and `/admin` are English only.                                                                                                                                                                                                     |
| B6  | Auto-reject of unaccepted orders runs on Supabase `pg_cron` (Vercel Hobby cron is daily only).                                                                                                                                                  |
| B7  | The branch dashboard has a "Start shift" button that unlocks audio (browser autoplay rules).                                                                                                                                                    |

The alias is all the plugin does without its experimental options.                        |

Search indexing is **off unless** `NEXT_PUBLIC_ALLOW_INDEXING=true` | A fresh deployment is always clearly a demo. Demo phone numbers might belong to real people, and a fictional restaurant shouldn't appear in search results.                                                                                                       |
| D17 | `/dashboard`, `/admin` and `/styleguide` sit outside locale routing, each area with its own root layout; `app/global-not-found.tsx` covers URLs outside both                            | Staff screens are English only (B5).                                                                                                                                                                                                                              |

| D20 | Vercel functions run in `hnd1` (Tokyo), set in `vercel.json`, next to the Supabase project (`ap-northeast-1`)                                                                           | Server renders and Server Actions make several database queries each; the default region (US East) would add a trans-Pacific round trip to every one. ## Added during Phase 2

| #   | Decision                                                                                                                                                                                                   | Reason                                                                                                                                                                                                  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D21 | Orders are created only by `public.place_order()`, callable with the secret key alone. The server validates and prices the cart (`src/lib/orders/quote.ts`), then passes the result in one call            | Atomic (order, items, history and promo redemption together), idempotent through the checkout's idempotency key, and the browser never writes to orders.                                                |
| D22 | Live tracking uses Supabase Realtime **broadcast** on a public topic `order:<token>`, sent by a database trigger. Payload: status, payment status and time                                                 | Guests aren't signed in, so RLS-filtered change feeds can't reach them. The topic contains the unguessable token, so only the holder of the tracking link can listen; the payload has no personal data. |
| D23 | Session cookies are **HttpOnly**. The header asks `/api/me` who is signed in                                                                                                                               | Page scripts can't read the tokens, so an XSS bug can't steal a session.                                                                                                                                |
| D24 | Promo codes aren't readable through the API; they're looked up with the secret key during a quote                                                                                                          | Prevents listing every code.                                                                                                                                                                            |
| D25 | Customer sign-in is email and password. Supabase's "Confirm email" decides whether sign-up needs a confirmation link (D10: without a custom SMTP domain, only project members receive it)                  | Social and phone sign-in need accounts or paid SMS.                                                                                                                                                     |
| D26 | Order journeys run in CI against a local Supabase stack (`supabase start`, database job); locally they run against any database with `E2E_DATABASE=1`                                                      | Ordering can't be tested on the seed fallback.                                                                                                                                                          |
| D27 | Delivery orders need a map pin; the nearest branch whose radius covers it is chosen automatically. Pickup lets the customer choose. Scheduled orders: 15-minute slots, from 30 minutes ahead, up to 3 days | Matches how Sri Lankan delivery works: landmarks and pins beat postcodes.                                                                                                                               |

## Added during Phase 3

| #   | Decision                                                                                                                                                                                                                                                                                                                                         | Reason                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D28 | An order paid online starts as `awaiting_payment` and reaches the branch (`received`) only when PayHere's signed server notification confirms the payment. Unpaid orders are cancelled after 30 minutes by a `pg_cron` job every 5 minutes, and their promo code use is given back                                                               | The kitchen never starts on an unpaid order, and abandoned checkouts don't hold promo codes.                                                                                                                              |
| D29 | PayHere's redirect checkout (a form post from `/checkout` or `/pay`), not its JavaScript popup                                                                                                                                                                                                                                                   | Works with the strict nonce CSP and `Cross-Origin-Opener-Policy: same-origin`; only `form-action` needs PayHere, on those two pages. PayHere checks the Referer, so payments never start from `/track`, which sends none. |
| D30 | Each trip to PayHere is its own `payments` row; PayHere's `order_id` is `<order number>-<attempt>`, up to 10 attempts                                                                                                                                                                                                                            | A declined or cancelled payment can be retried without reusing a PayHere order ID.                                                                                                                                        |
| D31 | Only notifications with a valid `md5sig` reach the database; the card holder's name, masked card number and expiry are dropped before storing                                                                                                                                                                                                    | Nothing we need (PDPA data minimisation). Forged notifications are refused before touching the database and logged to the server log.                                                                                     |
| D32 | PayHere runs only on the production domain: `PAYHERE_*` are set for Vercel Production only, and preview deployments offer cash payment. CI and the payment journeys stand in for PayHere with a made-up merchant                                                                                                                                 | PayHere's merchant secret belongs to one registered domain, and preview URLs change and sit behind Vercel's login, which would block PayHere's notification.                                                              |
| D33 | After a failed payment the customer can retry or, if `features.cashOnDelivery` is on, pay in cash. A payment that completes after that switch still wins. Payments arriving for a cancelled order or with the wrong amount are flagged for a person; until the admin panel (Phase 6) lists them, refunds are made in the PayHere merchant portal | Every failure path ends in a paid order, a cash order or a cancelled one, never a stuck one.                                                                                                                              |
| D34 | The tracking page re-checks the order when its live connection opens and every 20 seconds while live (10 seconds while offline)                                                                                                                                                                                                                  | Realtime broadcasts aren't replayed: a change made while the connection was opening, or while Supabase's listener was waking up, would otherwise be missed.                                                               |

## Added during Phase 5

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                         | Reason                                                                                                                                            |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| D42 | Table bookings are confirmed straight away when seats are free. Online bookings use up to 60% of a branch's seats at any moment (the rest is for walk-ins). A table is held 90 minutes, or 120 for parties of 7 or more. Slots every 30 minutes until an hour before closing, from 2 hours ahead up to 30 days. 1 to 12 guests; bigger groups use the events form. All of it is in `settings.brand.reservations` | Instant confirmation is what guests expect. Keeping seats for walk-ins and capping party size protects the dining room.                           |
| D43 | `book_table()` (secret key only) checks capacity under a per-branch lock, counting seats at the busiest moment of the new booking, and is idempotent                                                                                                                                                                                                                                                             | Two guests can't take the last seats at once. Counting the busiest moment, not every overlapping booking, doesn't turn away guests who would fit. |
| D44 | Each booking and enquiry has a private link (32-character token) for viewing and cancelling, like order tracking. Guests can cancel online up to 2 hours before                                                                                                                                                                                                                                                  | No account needed. Late cancellations go through the branch.                                                                                      |
| D45 | Events pipeline: enquiry (New) → the branch's manager or an admin sends a quote with an optional deposit (Quoted) → the guest accepts (Confirmed, or after the deposit is paid) → Done. Declining or cancelling needs a reason. Menus to start from are in `settings.brand.events.packages`                                                                                                                      | Matches how restaurants quote events. Staff can see enquiries; only managers and admins can price them.                                           |
| D46 | Deposits are PayHere payments linked to the enquiry, with reference `<enquiry ref>-<attempt>`, through the same signed notification handler as orders. Without PayHere the page says the branch will arrange the deposit, and managers can mark an event confirmed by hand                                                                                                                                       | One payment path to secure and test. The deposit is optional while PayHere is paused.                                                             |
| D47 | Database test files run one at a time (Vitest `db` project)                                                                                                                                                                                                                                                                                                                                                      | Each boots its own in-memory Postgres; five in parallel ran out of memory.                                                                        |

## Added during Phase 6

| #   | Decision                                                                                                                                                                                                                                                                                                                                             | Reason                                                                                                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D49 | Managers and admins must use two-step sign-in (TOTP authenticator apps). The database enforces it: admin and manager rights in `is_admin()`, `is_branch_staff()` and `is_branch_manager()` need a session at `aal2`; the app sends them to `/dashboard/security` until then. Optional for branch staff. | D51 | An audit log is written by database triggers: whole rows for catalogue, branch, holiday, promotion, promo code and settings changes; only the changed fields for staff roles, bookings, enquiries and branch secrets, to keep personal details out. The IP is the one our server saw (`x-client-ip`)                                                 | Covers every path, including future scripts.                                                                                                                                                                          |
| D52 | Images go to a public `media` storage bucket. Their type is read from their bytes (JPEG, PNG, WebP, AVIF), up to 3 MB; Server Actions accept up to 4 MB bodies for this                                                                                                                                                                              | A renamed file can't pass as an image; the bucket serves only what admins uploaded.                                                                                                                                   |
| D53 | Refunds are made in the PayHere merchant portal and recorded on the Payments page. Payments for rejected or cancelled orders, and for closed events, are listed as owed                                                                                                                                                                              | PayHere's refund API needs a separate business app and OAuth setup; a later upgrade.                                                                                                                                  |
| D54 | Brand settings are saved as overrides of `src/config/brand.ts`: only what differs is stored. Saving validates the whole brand and WCAG AA contrast for text colours                                                                                                                                                                                  | Later releases' new defaults still reach unchanged fields, and a rebrand can't make text unreadable.                                                                                                                  |
| D55 | Staff are added from existing accounts (they sign up first) or invited by email (delivery limited by D10). Admins can't change their own role                                                                                                                                                                                                        | Simple, auditable, and no admin can lock themselves out of the last admin account.                                                                                                                                    |
| D56 | Public pages refresh after admin and staff changes with `revalidatePath("/[locale]", "layout")` (src/lib/revalidate.ts). The locale layout no longer sets `dynamicParams = false`; unknown locales are refused with `notFound()`                                                                                                                     | With `dynamicParams = false`, `next start` served a 404 for every page revalidated on demand (found by the CI journeys when the admin test saved a dish). `"/"` names no layout here: the app has three root layouts. |
